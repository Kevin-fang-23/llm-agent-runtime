### 本次修复的缺陷（P0-2 修复：HITL 多轮审批用例恒失败）

**现象**：`test_multi_round_needs_approval_each_round` 确定性失败（单跑、全量跑均失败），报 `KeyError: 'status'`。

**取证过程**（写了独立复现脚本打印真实 HTTP 响应）：

```
submit  -> 202 {'id': '25babc3f3e1e', ...}
[waiting] status=waiting_approval  steps_used=1  tokens_used=855   checkpoint_next=["approval_gate"]
approve -> 202
  poll#0: status=waiting_approval  steps_used=1     <- 刚 approve，尚未推进
  poll#1: status=waiting_approval  steps_used=2     <- 已推进！第一轮工具跑完、第二轮又挂起
  poll#2..59: status=waiting_approval  steps_used=2 <- 一直是 waiting_approval
```

trace 事件流证明**运行时行为完全正确**：
```
#1 llm_step        thought='查北京' tool_calls=[web_search]
#2 approval_granted decision=True
#3 tool_result     tool=web_search  summary='搜索「北京 天气」命中 2 条…'
#4 llm_step        thought='查上海' tool_calls=[web_search]   <- 第二轮，又挂起等审批
```

**根因**：不是运行时缺陷，而是**测试辅助函数的竞态**。

`_wait_leave_waiting` 判据是「`status != "waiting_approval"`」。但对多轮审批任务，approve 后这一轮工具跑完会**立刻**在下一轮工具前**再次**挂起 —— 从外部观测，状态**从未**离开过 `waiting_approval`。于是轮询循环空转到 20s 超时。而 `KeyError: 'status'` 是超时前最后一轮请求恰逢任务行更新窗口的次生现象（报错信息掩盖了真实原因 TimeoutError）。

**为什么这个用例长期没暴露**：它是新加入 HITL 组件的用例，且失败信息是 `KeyError` 而非 `TimeoutError`，指向性很弱——看起来像"接口返回了非预期结构"，实际是"等待判据本身不成立"。

**修法**（`tests/test_hitl.py`）：改用**单调递增**量 `steps_used` 作为"这一轮确实过了"的证据。`steps_used` 在每轮 `react_step` 后递增（第一轮挂起时 = 1，审批放行并跑完第一轮工具后 = 2），跨轮不会回退，不会漏判。

```python
def _wait_leave_waiting(client, task_id, timeout_s=20.0,
                        bump_key=None, bump_at_least=0):
    ...
    if t.get("status") in TERMINAL:      # 已终态，直接成功
        return t
    if bump_key and int(t.get(bump_key, 0)) >= bump_at_least:  # 本轮确实推进了
        return t
```

**修复效果**：`tests/test_hitl.py` 8/8 通过，耗时从 **18.06s → 5.81s**（不再空等 20s）；全量 **205 passed**，总耗时 **38.66s → 24.91s**。

> ⚠️ 这个用例的价值恰恰在于它现在是"真的在测多轮审批"——修的是**判据**，不是**断言**。`assert t["status"] == "waiting_approval", "第二轮工具前应再次挂起"` 一字未动。

## 2. 核心实现逻辑（按数据流）

### 2.1 执行内核：LangGraph 六节点状态机

```
START → route_entry ─┬→ planner ──────────────→ react_step
                     └→ react_step
react_step → route_after_step ─┬→ approval_gate → route_after_gate ─┬→ tool_executor
                               │                                    └→ END（拒绝）
                               └→ finisher → END
tool_executor → critic → route_after_critic ─┬→ planner（重规划）
                                             ├→ compressor → react_step
                                             └→ finisher → END
```

**关键设计**：`route_after_step` 的 `"tool_executor"` 目标被有意指向 `approval_gate` 节点 —— 这样**所有**任务都经过审批门，由门内 `approval_gate_node` 判断 `require_approval` 后决定直接放行还是 `interrupt()` 挂起。好处是"审批"不是旁路分支，而是主路径上的一个必经关卡，非审批任务零额外成本。

### 2.2 checkpoint 与三种恢复语义

`app/config.py:28` 的 `checkpoint_durability: str = "sync"` 是一个**用实测代价换来的默认值**：

> LangGraph 1.x 的 `async` 档位只是把写盘**排队**而非即时落盘，进程被硬杀（kill -9 / TerminateProcess）时会丢掉最后几个 superstep 的 checkpoint —— 实测 12 次硬杀里 5 次丢到只剩初始状态，导致"崩了能恢复"实际不成立。`sync` 的代价是每个 superstep 多等一次写盘（吞吐会下降），这正是可恢复性的真实成本。

三种恢复语义在 `engine.resume_task` 中区分：

| 场景 | 调用 | 行为 |
|---|---|---|
| 崩溃后恢复 | `ainvoke(None)` | 从待执行节点继续 |
| HITL 审批 | `Command(resume=True/False)` | 跨越 `interrupt()`，节点重跑并放行/终止 |
| 无 checkpoint | `snap.next` 为空 | 直接返回当前值（无内容可恢复） |

第 3 种之外还有一个守卫：`resume_value is None` 但 checkpoint 上挂着未决 interrupt 时**主动抛错**（`"任务在等待人工审批，请通过 /approve 或 /reject 提供决策"`），而不是让 `ainvoke(None)` 静默失败。

### 2.3 工具执行流水幂等（at-most-once 的边界）

**checkpoint 落在 superstep 边界，节点内动作是 at-least-once。** 覆盖这个窗口的机制是 `ToolExecution` 表：

```python
class ToolExecution(Base):
    __table_args__ = (UniqueConstraint("task_id", "call_id", name="uq_tool_exec_task_call"),)
```

`tool_executor_node` 在**执行前**查流水、**执行后**写流水，`_execute_call` 是唯一出口。恢复时重跑 `tool_executor`，命中流水即发 `tool_replay` 事件并跳过执行。

**边界必须说清**（README 深挖点 6 已如实标注）：覆盖的是"工具已返回、流水已提交，但 checkpoint 尚未提交"这个崩溃窗口。**工具执行中途崩溃（流水还没写）拦不住** —— 那需要工具侧提供幂等键，属远程服务的责任。这个诚实标注比"我们做到了 exactly-once"更有说服力。

### 2.4 结构化错误码体系（这是"从猜文本到可枚举"的范式转换）

**改造前**：`"超时" in errors` —— 两个硬伤：改一句文案就失效；且 `httpx` 的超时文案是 `timed out`，与标记 `timeout` **并不匹配**，这整类错误被**静默判成"不可重试"**。

**改造后**三方共用一份契约（`app/core/errors.py`）：

```
registry.py       异常 → 带 code 的 ToolExecutionError（集中映射表 _EXCEPTION_CODE_MAP）
retry.py          按 code 判"是否值得原样重试"，读 retry_after_s 做退避提示
nodes.py::critic  按 code 分流：plan_defect / fatal / retryable
```

判定顺序刻意设计为**结构化优先、文本兜底**：`显式 retryable → 结构化 code → looks_transient 文本匹配`。这样"加固不改变既有行为"——未标注 code 的抛错点仍走原逻辑。

`ToolErrorCode` 用 `StrEnum` 而非 `(str, Enum)`，注释写明了原因：后者在 Python 3.11 下 `str(member)` 会得到 `"ToolErrorCode.TIMEOUT"`，且枚举 `__hash__` 基于成员名，与等值字符串哈希不一致 —— **跨 checkpoint 反序列化退回普通字符串后，集合交集会静默失配，分类逻辑悄悄退化成文本兜底**。这是一个只有真正踩过持久化+枚举交互的人才会写下的注释。

### 2.5 两级重试 + 自愈循环的升级阶梯

三种"失败处理"分工明确，互不越界：

| 机制 | 修什么 | 手段 | 上限 |
|---|---|---|---|
| 自愈循环 | **参数错**（schema 校验失败） | 回喂 REPAIR 提示词改参数后重跑 | `max_selfheal_retries=3` |
| 退避重试 | **运行错**（参数一字不改） | 指数退避原样重试 | `retry_max_attempts=2` |
| critic 分流 | 以上都用尽 | retryable→回决策 / plan_defect→重规划 / fatal→终止 | `max_steps` 兜底 |

**退避重试的三重闸门**（缺一不可，`nodes.py:_retry_transient`）：
1. 错误被判为瞬时（结构化 code 优先）；
2. **工具声明 `retry_transient`** —— 默认 False 是刻意的：*超时不等于失败，工具可能已经产生了副作用，盲目重试会把它做第二遍*。只有只读/天然幂等的工具打开（web_search / get_weather / db_query），写类与有副作用类（file_ops 的 write / code_run / subagent）一律关闭；
3. 未取消 —— 协作式取消要能立刻生效，不能卡在退避 sleep 里。

**自愈配额的并发安全**（一个隐蔽的坑）：原实现用任务级共享计数器，在 `asyncio.gather` 并行工具下互相挤占 —— 一个工具的修复会消耗另一个工具的配额。改为**协程内局部计数**，配额按"单次调用"计。

### 2.6 上下文压缩：为什么需要"关键输出不可压缩"

**摘要必然有损**，所以关键工具输出在**产生时**即复制进 `state.key_outputs`（截断快照），每步注入 system 并标记 `[关键数据（已确认，不可压缩，直接引用）]`。压缩只作用于"过程消息"，事实数据不走摘要。

窗口左边界必须落在 `assistant` 上 —— 孤儿 `tool` 消息会被 OpenAI 兼容接口拒绝，所以有：
```python
while recent and recent[0].get("role") == "tool":
    mid.append(recent.pop(0))
```

**踩过的坑（README 深挖点 9）**：早期把每轮现构造的 system / 任务提示也写回了历史，于是上一轮拼进去的"输入"在下一轮变成"历史"，上下文随步数近似 **O(n²)** 膨胀 —— 实测第 5 次 LLM 调用收到的 token 是第 1 次的 **26 倍**（202 → 5184），并连带打穿压缩器（它的切片假设 system 只出现在头部）。修法是把"每轮重建的输入"与"执行历史"拆成两条通道。

### 2.7 沙箱：为什么用 `argv` 传码而不是挂载文件

```python
container = self.client.containers.run(
    self.image,
    command=["python", "-I", "-c", code],   # ← 关键
    network_disabled=True, mem_limit="256m", nano_cpus=1_000_000_000,
    pids_limit=64, user="65534:65534", read_only=True,
    tmpfs={"/tmp": "size=32m"}, working_dir="/tmp",
)
```

**bind-mount 路径由 Docker daemon 按宿主机文件系统解析**，当引擎自身运行在容器内（compose worker）时该路径不存在，会挂载出空目录导致 `can't open file '/srv/code.py'`。用 argv 传码彻底规避。这个坑解得干净，注释也说明了原因。

安全模型防三件事：**数据外泄**（network_disabled）、**资源耗尽**（内存/CPU/进程数/时长四重限制）、**宿主污染**（只读根 FS + tmpfs /tmp + 非 root 65534）。

### 2.8 鉴权与多租户

- **明文 key 不落库**：只存 SHA-256 哈希；明文仅在创建/轮换时返回一次（与 GitHub PAT 同一模式）。**用 SHA-256 而非 bcrypt/argon2 是有理由的**：key 是 128 bit 随机数而非人类口令，没有弱熵可爆破，慢哈希只增加每次请求的验证延迟。
- **401 / 403 / 404 语义**：401 = 未认证；403 = 已认证但被禁用/非管理员；**跨租户读任务一律 404**（不泄漏任务存在性）。
- **key 提取顺序**：`X-API-Key` → `Authorization: Bearer` → `?api_key=`（**仅 /stream 端点**，因 EventSource 无法设置请求头；key 进 URL 有被代理/访问日志记录的风险，所以只对必须的端点放开）。
- **负缓存**：无效 key 也入缓存，防止撞库请求把查询打到 DB；容量超限整体清空（防撞库撑内存）。
- **零配置引导**：`AUTH_ENABLED` 默认开启；`ADMIN_API_KEY` 留空时首次启动生成，与 default 租户 key 一起写入 `data/api_credentials.json`（env 优先于文件）。轮换后若文件 key 与库中哈希不一致，**轮换出新的并回写文件**。

管理端点用 `secrets.compare_digest` 做常量时间比较，防时序侧信道逐字节猜 key。

### 2.9 四层限流：判定依据即事实来源

| 层 | 粒度 | 存储 | 位置 |
|---|---|---|---|
| L1 | 每 IP 每分钟 | 进程内滑动窗口 | ASGI 中间件（**鉴权之前**，撞库也计数） |
| L2 | 每租户每分钟提交数 | 进程内滑动窗口 | `_enforce_submit_limits` |
| L2b | 每租户每日提交数 | **tasks 表实数聚合** | 同上 |
| L3 | 全局每日提交数 | **tasks 表实数聚合** | 同上（真正的资金护栏） |
| L4 | 每租户每日 token | **实耗 + 在途预占** | 同上 |

**日级额度全部直接聚合 `tasks` 表，不另建计数器表** —— 理由是姊妹项目的真实教训：campus-assistant 的限流计数器曾因"内存判定 + 异步记账"实测超发 50%、又因"先读后写"在多进程下偶发超发 1 次，最后靠"单事务原子占位"才修稳。**直接聚合事实表更便宜且更不容易错**（代价是每次提交多两三条带索引的聚合查询，相对一次 LLM 调用可忽略）。

分钟级突发控制仍用进程内滑动窗口 —— 那层本就该按实例算，README 显式披露"多 worker 时额度 = 单实例 × worker 数"。

判定顺序也是刻意的：**便宜的内存判定在前，DB 聚合在后**。

### 2.10 优雅停机：先排空、后取消

`LocalTaskQueue.stop()` 的 docstring 记录了一个只有实机测试才能发现的坑：

> 在跑任务若在 DB 操作中途被 cancel，`CancelledError` 会打断 aiosqlite 连接的关闭流程 —— SQLite 文件句柄在 C 层孤儿化：Python 对象全部显示已关闭、无线程存活、`gc` 扫描一无所获，但进程存活期间该库文件永远无法删除（Windows 上表现为测试临时目录清理报 WinError 32；Linux 因"删除已打开的文件不报错"被长期掩盖）。**复现对照：提交任务后立即停机 100% 泄漏，等任务到终态再停机 0% 泄漏。**

修法：先等在跑任务自然结束（`shutdown_drain_timeout_s`，默认 10s），超时才 cancel 兜底 —— 这本来就是优雅停机应有的语义：让节点边界把状态落完，而不是半路掐断。

### 2.11 MCP 服务端：单一事实来源

`app/mcp_server.py` 的 `_signature_for` 用 `Annotated[类型, Field(...)]` 把 `description` 与 `minimum/maximum` 一起塞进函数签名。注释说明了为什么必须这样：

> SDK 是**从签名重新生成** schema 的，只给裸类型会丢掉这些语义（实测 code_run 的 description 与 1~60 的取值范围全被丢掉）。这是"单一事实来源"能否成立的关键。

`tools/call` 走 `registry.execute()`，因此沙箱隔离、JSON Schema 校验、结构化错误码、超时与 `retry_transient` 全部复用。且**只声明 tools 能力**，不实现 resources/prompts —— README 只声称 tools/list + tools/call，不夸大能力面。

## 4. 关键难点（按"含金量"排序）

### ★★★ 1. checkpoint durability 档位：可恢复性的真实成本
`async` 档位在硬杀下丢最后几个 superstep（12 次硬杀中 5 次丢到只剩初始状态）。默认改 `sync` 的代价是吞吐下降 —— **这个取舍本身就是指标**（46 → 21.3 tasks/s）。它证明作者理解"可靠性不是免费的"，而不是把参数调到最优看数字好看。

### ★★★ 2. 从字符串嗅探到结构化错误码
真正的收获不是"加了枚举"，而是发现 `httpx` 的 `timed out` 与标记 `timeout` **不匹配** —— 一整类超时错误被静默判成不可重试。**这类"静默的错误分类"是最危险的缺陷**，因为它不报错、只是行为不对。配套的 `StrEnum` 哈希陷阱注释说明作者验证过跨 checkpoint 反序列化路径。

### ★★★ 3. O(n²) 上下文膨胀（26 倍实测）
"每轮现构造的输入"写回历史 → 下一轮变成历史 → 指数级堆叠。这个缺陷的隐蔽性在于：功能看起来完全正常，只是账单在涨。修复方案（拆两条通道）比"修一个 bug"更有架构意义。

### ★★☆ 4. 工具执行流水幂等 + 边界诚实标注
以 `(task_id, call_id)` 为幂等键，覆盖"流水已提交、checkpoint 未提交"窗口；**明确声明覆盖不到"工具执行中途崩溃"**（需工具侧幂等键）。知道自己做了什么、更知道自己没做什么。

### ★★☆ 5. at-least-once 到 at-most-once 的语义分层
"checkpoint 落在 superstep 边界，节点内动作是 at-least-once" —— 这个表述本身说明作者真的想清楚了持久化语义，而不是含糊地宣称"支持断点续传"。

### ★★☆ 6. 自愈配额的协程级隔离
共享计数器在 `asyncio.gather` 下互相挤占 —— 一个并发维度引发的配额串扰。改为协程内局部计数后，配额语义从"任务级"精确到"调用级"。

### ★★☆ 7. 来源可信度分级 + 反爬/结构变更分层
搜索场景下模型把 3 条互不相干的结果**拼凑**成完全错误的结论（还自称"关键信息具有一致性"）。修法是三层：工具标注来源可信度 + 提示词写死冲突判定顺序与严禁拼凑 + 不许以"预算不足"为由带疑问给确定答案。
另外**"被反爬限流"与"页面结构变更"是完全不同的两件事** —— 前者等一会儿重试（`RATE_LIMITED` 可重试），后者才需要改解析器。混为一谈会让人改错地方。

### ★★☆ 8. 优雅停机的"先排空后取消"
`CancelledError` 打断 aiosqlite 关闭流程 → SQLite 句柄在 C 层孤儿化（Python 层完全看不到）。这个缺陷在 Linux 上**永远暴露不出来**（删除已打开的文件不报错），只在 Windows 上表现为 `WinError 32`。100% vs 0% 的复现对照极其干净。

### ★☆☆ 9. 限流判定用事实来源而非计数器表
把姊妹项目踩过的坑（内存判定超发 50%、多进程超发 1 次）转化成架构选择：日级额度直接聚合 `tasks` 表。代价可量化（每次提交多 2~3 条索引查询 vs 一次 LLM 调用）。

### ★☆☆ 10. Docker 沙箱的 `argv` 传码
一句话解决 `can't open file '/srv/code.py'`：daemon 按宿主机解析 bind-mount 路径。

### ★☆☆ 11. MCP schema 单一事实来源
从 JSON Schema 反推函数签名，用 `Annotated[..., Field(...)]` 保住 description 与取值范围 —— 否则 SDK 重新生成的 schema 会丢语义。
