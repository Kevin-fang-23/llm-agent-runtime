## 一、先给结论：这个项目该不该写？

**该写，而且应该作为第二个核心项目写在 campus-assistant 之后。**

理由是它和 campus-assistant 构成**互补叙事**，而不是重复：

| | campus-assistant | llm-agent-runtime |
|---|---|---|
| 证明什么 | 能把 AI 应用**做对** | 能把 AI 应用**做稳** |
| 技术挑战 | 检索准不准（确定性流水线，人是架构设计者） | 规划对不对、执行安不安全、崩了能不能恢复、成本可不可控 |
| 你的角色 | 架构设计者 | **给模型造安全护栏的人** |
| 关键技术 | FAISS/BM25/RRF/OCR/VLM | LangGraph 状态机/checkpoint/沙箱/幂等/多租户 |

面试官看完 campus-assistant 会问："那你会不会做 Agent？"——这个项目就是答案。

**但必须先做一件事**：见第四节「必须先修的三件事」。数字对不齐会直接反噬"用数据说话"的人设。

### 版本 A：完整版（适合一页简历的"重点项目"位置）

**LLM Agent Runtime · 个人项目 · 面向真实业务的可托管 Agent 运行时**
`Python · LangGraph · FastAPI · SQLAlchemy 2.0 · Docker · Celery/Redis · PostgreSQL · MCP`
[github.com/Kevin-fang-23/llm-agent-runtime](https://github.com/Kevin-fang-23/llm-agent-runtime) （已开源）

- **执行内核**：基于 LangGraph 构建七节点状态机（planner / react_step / approval_gate / tool_executor / critic / compressor / finisher）+ 条件边；ReAct 与 Plan-and-Execute 双模式路由进同一状态机，critic 检出"计划缺陷"自动回 planner 重规划（只补剩余步骤）。选用状态机而非自由循环，是为了同时拿到**可控**（路由显式）、**可持久化**（superstep 边界即 checkpoint 点）、**可恢复**（`ainvoke(None)` 续跑）、**可观测**（节点边界即事件边界）四项性质。

- **中断恢复（量化）**：checkpointer 落 SQLite/PostgreSQL，进程崩溃后从断点续跑。实测**断点恢复成功率 100%（n=10，磁盘 checkpoint + 关闭连接后用全新连接恢复）**、**崩溃恢复成功率 100%（n=5，子进程被硬杀后换进程恢复至完成）**。
  - 关键取舍：默认 durability 设 `sync` 而非框架默认的 `async` —— 实测 `async` 档位只是把写盘**排队**，硬杀进程时 12 次里 5 次丢到只剩初始状态，"崩了能恢复"实际不成立。代价是吞吐下降（46 → 21.3 tasks/s），**这是可恢复性的真实成本**。

- **工具执行幂等（at-most-once）**：checkpoint 落在 superstep 边界，节点内动作是 at-least-once。新增 `tool_executions` 表以 `(task_id, call_id)` 为唯一幂等键，覆盖"工具已返回、流水已提交，但 checkpoint 未提交"的崩溃窗口，恢复时按流水**回放结果而非重复执行**。边界已如实标注：工具执行**中途**崩溃（流水未写）拦不住，需工具侧提供幂等键，属远程服务责任。

- **错误处理从"猜文本"到"可枚举"**：将原先的中文关键词嗅探（`"超时" in errors`）改造为**结构化错误码契约**（timeout/network/rate_limited/upstream_5xx/auth/permission/not_found/invalid_args），registry / retry / critic 三方共用。改造中定位到一个静默缺陷：`httpx` 的超时文案是 `timed out`，与嗅探标记 `timeout` **不匹配**，导致整类超时错误被判为"不可重试"。判定顺序设计为「显式 retryable → 结构化 code → 文本兜底」，保证加固不改变既有行为；并补齐 `Retry-After` 优先、HTTP 5xx/429/404 分流这些嗅探覆盖不到的场景。

- **两级重试 + 自愈的升级阶梯**：自愈修**参数错**（schema 校验失败 → 回喂 REPAIR 提示词重跑，实测**自愈挽救率 100%，n=10**）、指数退避重试处理**运行错**（参数一字不改）。重试设三重闸门：瞬时性判定 + **工具显式声明 `retry_transient`**（默认关闭 —— 超时不等于失败，有副作用的工具盲目重试会做两遍，故仅只读工具开启）+ 未取消。两者用尽后由 critic 按错误码分流至重规划/终止，**不在工具层无限重试**。
  - 并修复一处并发缺陷：自愈配额原为任务级共享计数器，在 `asyncio.gather` 并行工具下互相挤占；改为协程内局部计数，配额语义从"任务级"精确到"单次调用"。

- **Docker 沙箱隔离**：`network_disabled` + `mem_limit` + `nano_cpus` + `pids_limit=64` + `read_only` + `tmpfs /tmp` + 非 root（uid 65534）七项加固，防数据外泄 / 资源耗尽 / 宿主污染三类风险。代码经 `python -I -c` argv 直接传入**不做文件挂载** —— bind-mount 路径由 daemon 按宿主机解析，引擎自身在容器内时该路径不存在（`can't open file '/srv/code.py'` 的根因）。以上四项均有自动化集成测试断言（无挂载可执行 / 出网被拦 / uid=65534 / 超时被杀）。

- **鉴权 · 多租户 · 四层限流**：API Key 只存 SHA-256 哈希、明文仅创建时返回一次；租户隔离下**跨租户一律 404**（不泄漏任务存在性）；四层额度 = 每 IP 每分钟 → 每租户每分钟 → 每租户/全局每日提交数 → 每租户每日 token 配额（**实耗 + 在途按 `max_tokens` 预占**）。
  - 架构选择：日级额度**直接聚合 `tasks` 表**而非另建计数器表 —— 判定依据即事实来源，重启/多 worker/重复提交都不会漂移。这是把姊妹项目踩过的坑（内存判定实测超发 50%、多进程偶发超发 1 次）转化为设计决策。

- **MCP 服务端**：`app/mcp_server.py` 以 stdio 传输实现 `tools/list` + `tools/call`，可被任意 MCP 客户端接入；工具 `inputSchema` **直接复用 registry 的 JSON Schema**（单一事实来源，避免两处漂移），调用复用 `registry.execute()` 因而沙箱/校验/结构化错误码/超时全部继承。

- **工程护栏**：GitHub Actions 四道门禁 —— `static`（ruff E9/F63/F7/**F82 未定义名** + compileall + 两个进程入口导入冒烟）/ `test`（**205 条离线用例**，含注入敌对 `SEARCH_PROVIDER=bing` 的对抗步骤）/ `integration`（Docker 沙箱 4 例 + PG checkpoint 2 例 + 租户列迁移 1 例 + Celery/Redis 真实 broker 往返 3 例）/ `smoke`（CLI 全链路 + 崩溃恢复 + **指标门禁**：恢复率与自愈率断言 100%）。
  - `static` 这道门禁的直接成因：曾因 `runtime.py` 漏 `import get_settings` 导致 Windows 上 `import app.main` 直接 NameError，服务与 worker 双双起不来，而单元测试无人 import `app.main`、直到 API 用例收集失败才暴露。F82 能在 20 秒内拦住这类缺陷。

- **轨迹可视化**：每个节点广播事件流落库，Web 时间线经 **SSE 推送**实时渲染（无轮询）、工具参数/结果可折叠、计划进度 chip、token/步数进度条；轨迹可导出 JSON / Markdown 便于复盘。

## 五、简历排版的三个具体建议

1. **把两个项目并列，用一个"组合叙事"的定位句开头**（放在简历项目区最上方或个人评价里）：
   > 两个项目构成互补验证：**campus-assistant 证明能把 AI 应用做对**（多模态 RAG 流水线，检索质量可量化）；**llm-agent-runtime 证明能把 AI 应用做稳**（动态执行系统，崩溃可恢复、工具可幂等、成本可管控、多租户可隔离）。

2. **不要在 llm-agent-runtime 里堆功能清单**。你的 campus-assistant 条目已经写得很满（1410 字符），这个项目如果也堆满，两个项目会互相稀释。建议**每条都带一个"取舍"或"踩坑+修复"**——这是区分"用过框架"和"理解了系统"的分水岭，也正是你手里素材最扎实的部分。

3. **数字永远带口径**。你已经在 campus-assistant 里做到了（"混合 MRR@5 0.972、如实记录纯 BM25 更高 0.980"、"88.8µs/请求"、"4 子进程共享额度 40 实测放行 40 次"）—— **这种诚实度是这个简历最强的差异化优势，继续保持**。本项目的对应做法：
   - ✅ 写"断点恢复 100%（n=10，磁盘 checkpoint + 换连接）"
   - ❌ 不要写"断点恢复 100%"（没口径 = 不可信）
   - ✅ 写"崩溃恢复 100%（n=5，子进程硬杀）"
   - ✅ 写"吞吐 ≈21 tasks/s（m=20，并发 4，**含 SQLite checkpoint 落盘**）"——**"含落盘"这三个字必须留着**，它是这个指标的意义所在
   - ⚠️ 本次复跑实测 **18.73 tasks/s**（同协议、同机器、不同次运行）。README 写"≈21"是合理的（随机器变化已披露），但如果你要写进简历，建议写 **"≈20 tasks/s"** 或用区间，避免面试官复跑后质疑精确值。
