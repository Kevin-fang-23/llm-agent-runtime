# 别人怎么访问：三条路径与 API Key 的填法

> 本文回答一个问题：**除了你自己在这台电脑上双击启动，别人（同事 / 招聘官 / 公网访客）要怎么进来，那个 API Key 从哪来、填在哪。**

## 一句话结论

| 访问者在哪 | 需要 Key 吗 | Key 从哪来 | 填在哪 |
|---|---|---|---|
| 你自己的电脑（`127.0.0.1` / `localhost`） | **不需要** | — | — |
| 同一局域网的别人（`192.168.x.x`） | **需要** | `data/api_credentials.json` 里的 `default_tenant_key` | 页面右上角徽标点击 → 弹窗粘贴 |
| 公网（ngrok / 反向代理） | **需要**（见下方告警） | 同上，或为对方单独新建租户 | 同上 |

## 排障：页面提示「需要 API Key / 未完成 API 授权」怎么办

服务端有内置自检，**双击 `start.bat` 后会直接告诉你当前鉴权状态**：

```
鉴权状态：本机免密已生效 —— 页面打开即可直接提交任务，无需任何 API Key。
```

如果看到的是下面这句，说明免密没生效，按列出的原因排查：

```
[注意] 鉴权状态：本机免密**未生效**，页面会要求填写 API Key。
```

**先做这一步**：确认你访问的是 `http://127.0.0.1:<端口>` 而不是别的主机名。
页面本身会给出可点击的徽标提示，点开粘贴 `default_tenant_key` 即可继续。

### ⚠️ 最容易踩的坑：浏览器里那个「旧标签页」指向的不是本次启动的服务

这是实测中**最常见**的一类"未授权/提交失败"，而且服务和配置其实**完全正常**。

发生机制：

1. 上一轮你用过 `http://127.0.0.1:8000`，浏览器留着这个标签（或开着"恢复上次会话"）；
2. 这一轮双击 `start.bat` 时，8000 还**被上一轮那个没退干净的服务占着**（或你另开了别的东西占用 8000）；
3. 启动脚本检测到占用，**顺延到 8001** 并成功启动 —— 脚本本身没做错；
4. 但那个旧标签页**不会自动跳转**，它继续敲 8000，敲到的是**上一轮那个旧进程**（旧代码 / 旧配置，甚至在关停中途）。
   于是你看到一个"看起来是新版本、实际连错后端"的页面，报未授权。

**怎么区分"连错后端"和"真的没授权"**：

- 页面右上角显示 **「连接失败」** → 请求没到达任何服务（网络/端口问题）；
- 页面右上角显示 **「需 API Key」** → 请求**到达了**某个服务，但那个服务判定你来源非回环；
  **如果同时你访问的就是 `127.0.0.1`，那几乎可以断定是旧标签页连到了别的进程。**

**处理**：

- **已缓解**：`start.bat` 现在会在选端口**之前**先回收"**确认属于本项目**"的遗留服务进程
  （按命令行是否含 `serve_dualstack.py` / `app.main` 判定，绝不误杀别人的程序），
  这样 8000 能被顺利复用；真的顺延时，脚本会**显式警告**"旧标签页指向的不是本次启动的服务"。
- **手动**：直接双击 `scripts\stop.bat` 停掉全部旧服务，再重新双击 `start.bat`；
  然后用脚本横幅里打印的那个地址**开新标签页**（别用旧标签刷新）。

### 已知的导致"未授权"的原因（按概率排序）

> **2026-09-21 重要更正**：下表第一行此前写的是"浏览器旧标签页连到上一轮残留的旧服务"。
> 经实机复现（复现脚本 + 服务端日志取证），**那不是主因**。真正的首要原因见下面第一行。
> 旧标签页那条仍然成立，但它只是次要情形，且真正起作用的是**每 IP 每分钟限流**。

| 原因 | 现象 | 修法 |
|---|---|---|
| **请求频率超过每 IP 每分钟限额（429）被前端误显示成"未授权"** | 页面能开，但提交/刷新报"未授权"；服务端日志里 `GET /api/tasks` 每 4 秒 401/429 一次 | **已修复**：① 后端 L1 只拦写操作，GET 轮询豁免；② 前端把 429 与 401 彻底分开（429 提示"请求过于频繁"并给出 `Retry-After`）。详见下方专节 |
| **浏览器旧标签页连到上一轮残留的旧服务** | 页面看似正常但报未授权 / 提交失败 | **已缓解**：`start.bat` 启动前回收本项目遗留进程；手动可先跑 `stop.bat`，再用横幅地址开新标签 |
| 浏览器配了外部代理，请求经代理发出 | 对端地址不是回环 | 把 `127.0.0.1` 加入浏览器代理例外（NO_PROXY） |
| **用 `localhost` 访问，且浏览器解析到 `::1`** | 页面打不开或报未授权 | **已修复**：启动脚本现用 `serve_dualstack.py` 同时监听 IPv4 与 IPv6 回环 |
| 访问地址不是 `127.0.0.1`（如从局域网 IP 进） | 明确提示缺 Key | 属正常行为，按本文「路径 2」发 Key |
| `.env` 里设了 `AUTH_LOCALHOST_BYPASS=false` | 自检报未生效 | 删掉该行或改为 `true`，重启 |

### 为什么"限流"会被显示成"未授权"（已修复）

这是 2026-09-21 实机复现并修复的真实缺陷，值得单独说明，因为它是一个
**错误被错误分类**的典型：症状指向鉴权，真因却在限流层。

**取证结论（可复现）**：

```
L1 限额 = 每 IP 每分钟 120 次（IP_RATE_LIMIT_PER_MIN）
实测：第 120 次请求开始返回 429，响应体
      {"detail":"请求过于频繁（每 IP 每分钟 120 次），请稍后重试"}
滑动窗口，等待 60 秒后自动恢复（非永久封禁）
```

**放大链路**（这才是打满额度的原因，全部有代码依据）：

| 触发 | 实际请求数 |
|---|---|
| `refreshDetail()`（旧实现内含 `refreshList()`） | 3 次：取单任务 + 取列表 + 取指标 |
| `selectTask()` | 再叠加 `refreshDetail()` + 开 SSE 流 |
| **SSE 流结束 / 断流** | **再次回跳 `refreshDetail()`** → 自反馈循环 |
| 4 秒轮询 `refreshList()` | 2 次/轮 |

**两个缺陷让 429 变成了"未授权"**：

1. `api()` 正确区分了 429 并提示限流，但页面另有手写 `fetch`（SSE 流、导出）
   只照搬了 401 文案 → **限流被显示成鉴权失败**，排查方向被带偏。
2. 轮询的异常被 `.catch(() => {})` 静默吞掉 → 界面毫无提示，
   服务端却留下一串 401/429 日志，"数据莫名不动"无从归因。

**修复后**：

- 后端：L1 只拦写操作（`GET`/`HEAD`/`OPTIONS` 豁免）。撞库仍由 `require_tenant`
  的负缓存挡住，资金护栏仍在 L2b/L3/L4 的日级 `tasks` 表聚合，**写路径额度不变**。
- 前端：所有请求的错误处理收敛到单一 `httpError()`；429 如实提示并带
  `Retry-After`；轮询失败走节流提示（15 秒最多一次）；`refreshDetail()` 不再
  顺带刷新列表，消除放大。
- 握手失败时**不再启动轮询**（旧实现会每 4 秒打一串注定失败的请求）。

**如果你在旧版本上遇到这个现象**，临时缓解：等 60 秒，或把
`IP_RATE_LIMIT_PER_MIN` 调大，或减少页面刷新频率。

## ⚠️ 使用 ngrok 时有一个必须知道的边界

「本机免密」的判定依据是 **TCP 连接的对端地址**（socket peer），不是 HTTP 请求头里写的来源。
这么做是对的 —— `X-Forwarded-For` 客户端可随意伪造，信它等于把鉴权交给攻击者（已实测：伪造该头得到 401）。

**但这带来一个 ngrok 特有的问题：**

```
外部访客  →  ngrok 云端  →  ngrok 本机进程  →  你的服务
                              ↑
                    这里对端是 127.0.0.1
```

ngrok 把外部请求转发到你的服务时，**socket 对端是 ngrok 的本机进程**，也就是 `127.0.0.1`
→ 会被判定为「本机」→ **免密放行**。

**这意味着：如果你用 ngrok 分享链接，公网访客实际上不需要 Key 也能用，且烧的是你的
LLM 额度。** 这与「公网仍需密钥」的初衷相反。

### 两种处理方式

| 方案 | 做法 | 适用 |
|---|---|---|
| **A. 接受免密，但设配额护栏** | 保持现状，但给 default 租户设一个较小的 `daily_token_quota` | 短期演示、信任访客 |
| **B. 强制全链路要密钥** | `.env` 设 `AUTH_LOCALHOST_BYPASS=false`，重启 | 长期公开、不信任访客 |

方案 B 的具体代价：**你自己本机打开页面也要填一次 Key**（存在浏览器 localStorage，填一次即可）。

## 三条路径的详细操作

### 路径 1：本机（已验证免密）

双击 `scripts/start.bat` → 浏览器打开 `http://127.0.0.1:8000` → 页面右上角显示绿色 **「本机免密」** 徽标，无任何 Key 输入框，直接提交任务即可。

**取证**（真实服务端实测）：
```
[本机 127.0.0.1 访问]  status=200  mode=passwordless
```

---

### 路径 2：局域网内的别人（需要 Key）

对方用你在局域网里的地址访问，例如 `http://192.168.1.5:8000`。

**注意**：`start.bat` 启动的服务默认**只监听 127.0.0.1**，局域网里的别人**根本连不上**。
要让他们访问，得让服务监听 `0.0.0.0`。

**取证**：监听 `0.0.0.0` 后，从网卡地址访问的结果是：
```
[从网卡 IP 192.168.1.5 访问]           status=401  {'detail': '缺少 API Key（X-API-Key 请求头）'}
[从网卡 IP 192.168.1.5 带 Key 访问]    status=200  via=api_key
```
即：**必须给 Key，给了就能通**。

#### 给对方什么 Key

从 `data/api_credentials.json` 取 `default_tenant_key`：

```json
{
  "admin_api_key": "adm-<你的本机生成的 32 位 hex>",
  "default_tenant_key": "art-<你的本机生成的 32 位 hex>"
}
```

> ⚠️ **这里刻意不写真实值**：`data/` 已被 `.gitignore` 排除，密钥永远不会进版本库，
> 所以文档里也不应该出现具体值 —— 本文档是公开的，写进去等于把密钥发给每个能看仓库的人。
> 打开你本机的 `data/api_credentials.json` 取真实值即可（首次启动自动生成）。

**把 `default_tenant_key` 的值给对方**，让对方在页面右上角徽标处粘贴。

> 更稳妥的做法是**为对方单独建一个租户**（见下节），这样配额独立、可随时撤销、
> 出问题不影响你自己的 default 租户。

## 为别人单独开一个 Key（推荐做法）

管理端点和租户端点是**两套独立凭据**，不能混用（已实测：把 admin key 塞进
`X-API-Key` 会得到 401）。

```bash
# 用 X-Admin-Key 建一个新租户，指定每日 token 配额（单位：token）
curl -X POST http://127.0.0.1:8000/api/admin/tenants \
  -H "X-Admin-Key: <你的 admin_api_key>" \
  -H "Content-Type: application/json" \
  -d '{"name": "guest-alice", "daily_token_quota": 50000}'
```

响应里会**一次性**返回明文 key（之后任何接口都不再返回）：

```json
{ "id": "t-...", "name": "guest-alice", "api_key": "art-....", "..." : "..." }
```

把这个 `api_key` 给对方即可。

**配额护栏**：`daily_token_quota` 是最有效的防线 —— 即使对方乱用，
烧掉的量也有上限。建议按「演示一次大约需要多少 token」的 3~5 倍来设。

### 配套管理命令

```bash
# 列出所有租户（不含任何密钥字段）
curl http://127.0.0.1:8000/api/admin/tenants \
  -H "X-Admin-Key: <admin_api_key>"

# 查看某租户今日用量（实耗 + 在途预占）
curl http://127.0.0.1:8000/api/admin/tenants/<tenant_id>/usage \
  -H "X-Admin-Key: <admin_api_key>"

# 轮换密钥（旧 key 立即失效，返回新 key —— 用于「收回某个人的访问权」）
curl -X POST http://127.0.0.1:8000/api/admin/tenants/<tenant_id>/rotate \
  -H "X-Admin-Key: <admin_api_key>"

# 禁用租户（比删除更安全，可逆）
curl -X PATCH http://127.0.0.1:8000/api/admin/tenants/<tenant_id> \
  -H "X-Admin-Key: <admin_api_key>" \
  -H "Content-Type: application/json" \
  -d '{"enabled": false}'
```

## 对方在页面上怎么填

1. 打开页面，右上角会显示**橙色/黄色徽标**：`🔑 需 API Key（点击配置）`
2. **点击这个徽标**，弹出输入框
3. 粘贴 Key，确定
4. 徽标变成 `🔑 已配置密钥`，即可正常使用

Key 保存在该浏览器的 `localStorage`（键名 `agent_api_key`），**刷新不用重填**。
页面**从不回显**它，也**从不**把它写进 URL。

> 为什么不在页面上直接把 Key 预填好？因为 HTML 是公开的 —— 任何能打开页面的人
> 都能看到源码里的 Key。所以「内置密钥」这个方案在**纯前端**是不可行的，
> 必须由访问者自己持有。这也是「免密的判定放在服务端、按来源地址做」的原因。

## 决策速查表

| 你的场景 | 建议做法 |
|---|---|
| 自己演示、录屏 | 直接双击 `start.bat`，无需任何配置 |
| 给同宿舍/同办公室的人看 | 服务监听 `0.0.0.0` + 发 `default_tenant_key`（或建专用租户） |
| 交给招聘官试用（公网链接） | **设 `AUTH_LOCALHOST_BYPASS=false`** + 建一个低配额专用租户，把 key 随链接一起给出 |
| 完全不想管 Key | 建专用租户 + 设小配额，接受链接泄露的风险上限 |

## 相关配置项

| 配置项 | 默认 | 说明 |
|---|---|---|
| `AUTH_ENABLED` | `true` | 总开关。关掉等于任何人可烧 token，仅限本机开发 |
| `AUTH_LOCALHOST_BYPASS` | `true` | 回环来源免密。**用 ngrok 分享时建议设 `false`** |
| `TRUSTED_PROXY_HOPS` | `0` | 默认完全不信任 `X-Forwarded-For`。只有自建反向代理且代理会覆写该头时才设 >0 |
| `TENANT_DEFAULT_DAILY_TOKEN_QUOTA` | `2000000` | 新租户默认每日 token 配额（0 = 不限）；深检索任务一次实耗 6万~13万 token |
| `ADMIN_API_KEY` | 空 | 留空则首次启动生成并写入 `data/api_credentials.json` |

---

*本文数字均有实测取证：本机免密、局域网要求密钥、伪造 `X-Forwarded-For` 无效、
管理端点与租户端点凭据分离、密钥轮换后旧 key 立即 401 —— 共 29 项断言全绿，
运行在隔离的临时数据库上。*
